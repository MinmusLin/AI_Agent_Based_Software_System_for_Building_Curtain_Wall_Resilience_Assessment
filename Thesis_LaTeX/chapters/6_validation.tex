\chapter{系统验证与应用分析}
\label{chap:validation}

前文已经从研究背景、需求分析、技术方案和工程实现四个层面说明了本系统的设计与实现逻辑，本章在上述基础上对系统进行验证与应用分析。本章的验证目标是本系统是否能够把 Agent 自主任务调度、原子检测能力、人工复核、LLM 分层信息整合和工程状态机连接为可运行的软件闭环。换言之，本章关注的是系统是否真正完成了“从图像资产到韧性评估报告”的工程链路，是否能够支撑实际幕墙数字运维场景中的使用需求。

\section{验证目标}
\label{sec:validation-objective}

系统验证围绕三条主线展开。第一条主线是项目级图像资产管理，即系统是否能够支持项目创建、基础信息维护、图像组组织、批量图像上传、图像状态追踪和对象产物管理。第二条主线是 Agent 自主任务调度，即分类 Agent 的语义判断是否能够转化为受控任务代码，并进一步驱动后续原子检测任务创建、执行和状态推进。第三条主线是 LLM 分层信息整合，即单图检测结果是否能够生成图像级总结，项目级多源信息是否能够进一步汇总为可阅读、可复核的韧性评估报告。

围绕上述目标，验证工作分为功能验证、Agent 调度方法验证、LLM 分层整合策略验证、状态一致性验证、部署验证和验证结果展示六个方面。功能验证关注用户能否完成完整流程；Agent 调度方法验证关注分类输出是否真实影响检测任务；LLM 分层整合策略验证关注报告生成是否建立在结构化源数据和图像级总结之上；状态一致性验证关注数据库、后端任务、消息事件和前端展示是否保持一致；部署验证关注 Docker 环境下多服务是否能够正常协同；验证结果展示则用于集中呈现上述验证结果、系统运行界面和软件效果。

\section{功能验证}
\label{sec:validation-functional-validation}

功能验证覆盖用户从进入系统到生成评估报告的完整操作流程，包括注册登录、项目创建、项目基础信息维护、图像组管理、图像上传、批量操作、Agent 智能检测、检测结果查看、人工复核、项目报告生成和报告打印等环节。该部分验证的重点不是单个页面是否能够打开，而是多个业务阶段能否按照\cref{chap:requirements}定义的项目流程连续推进，并在每个阶段形成可查询、可恢复的结构化状态。

验证结果表明，系统完成了从项目基础信息到项目报告生成的端到端流程。项目基础信息能够保存建筑名称、建筑位置、建成年份、建筑描述、已知问题和评估目标等内容，并在阶段推进前完成自动提交；图像资产阶段能够完成图像组创建、图像上传、图像移动、图像删除、原图查看和批量操作，并形成项目、图像组、图像元数据和对象存储路径之间的结构化关系；Agent 智能检测阶段能够创建检测主任务并进入后台异步执行流程，用户能够查看图像级进度、节点级状态、任务 ID、失败状态和重试入口；检测完成后，系统能够展示图像数据、各子任务指标、检测产物、图像级 Agent 总结和人工复核区域；人工复核结果能够保存到数据库并参与项目报告上下文；报告生成阶段能够触发项目级报告生成，并在报告完成后展示结构化报告内容。

该验证表明，本系统覆盖了任务创建、Agent 自主任务调度、原子检测执行、产物上传、回调落库、RocketMQ 事件、WebSocket 推送和前端状态合并等多服务协同链路，由此证明系统已经具备从用户操作到后台任务再到前端反馈的完整业务闭环。

\section{Agent 自主任务调度方法验证}
\label{sec:validation-agent-autonomous-task-scheduling-validation}

Agent 自主任务调度方法验证覆盖分类 Agent 输出、任务代码解析、任务代码治理、主任务执行标记设置、检测子任务创建和空任务集合处理等环节。根据\cref{sec:design-agent-autonomous-task-scheduling-method}的设计，分类 Agent 并不直接返回自然语言说明，而是输出受控任务代码集合；BIZ 服务负责将该集合转换为后续检测流程中的任务执行计划。

实际验证表明，系统能够将分类 Agent 的输出稳定转换为检测任务。若输出 \texttt{crack} 和 \texttt{stain}，系统创建石材裂缝和石材污渍子任务；若输出 \texttt{flatness} 和 \texttt{spalling}，系统创建玻璃平整度和玻璃爆裂子任务；若输出 \texttt{corrosion}，系统创建金属锈蚀子任务；若输出空列表，系统不创建子任务和图像总结任务，并将主任务推进到成功状态。分类 Agent 的输出真实影响后续检测路径，而不是只作为展示文本存在。

该部分验证同时确认了服务端治理逻辑的有效性。分类输出能够被解析为合法 JSON 对象，任务代码被限制在固定集合内，非法任务代码被拦截，重复任务代码被去重，最终任务集合按照固定顺序归一化。通过这些约束，系统将开放语义判断转化为工程系统可消费的有限任务集合，验证了本文将 Agent 作为“受控任务规划节点”的设计思路。

\section{LLM 分层信息整合策略验证}
\label{sec:validation-large-language-model-hierarchical-information-integration-validation}

LLM 分层信息整合策略验证覆盖图像级总结和项目级报告两个语义层次。根据\cref{sec:design-large-language-model-hierarchical-information-integration-strategy}的设计，系统不直接把所有底层区域 JSON 一次性输入项目报告 Agent，而是在图像级先完成信息压缩和语义整理，再将项目基础信息、图像组、图像数量、检测任务、图像级总结、人工复核意见和报告源数据组织为项目级报告上下文。

验证结果表明，原子检测完成后，系统能够将结构化检测结果、执行任务代码、图像元数据和检测产物信息整理为图像级总结输入，Summary 服务能够生成图像级总结并回调 BIZ 保存。项目报告生成时，系统能够汇总项目级多源信息，生成报告源数据，并将该上下文保存到对象存储中供项目报告 Agent 通过附件方式读取。项目报告 Agent 输出后，系统能够对固定 JSON 结构进行压缩、解析和字段校验，并将报告结果写入数据库。

该验证表明，图像级总结回答“这一张图像说明什么”，项目级报告回答“整个项目说明什么”。图像级总结减少了底层指标直接进入项目报告的上下文压力，项目报告 Agent 则能够围绕跨图像缺陷分布、区域风险、整体韧性和维护建议形成更高层次的评估结论。因此该策略验证了本文从单图检测结论走向建筑级韧性评估结论的必要路径。

\section{状态一致性验证}
\label{sec:validation-state-consistency-validation}

状态一致性验证覆盖数据库状态、后端 Worker 执行状态、RocketMQ 项目事件、WebSocket 实时消息和前端页面状态之间的一致关系。系统通过项目阶段状态、图像上传状态、检测主任务状态、检测子任务状态、图像总结状态和报告生成状态共同表达业务进度；页面刷新时通过查询接口恢复数据库事实状态，实时运行时通过 WebSocket 接收增量事件。

验证结果表明，系统能够按照状态机规则推进任务状态。分类失败后主任务进入失败状态，子任务失败后主任务最终进入失败状态，所有必要子任务成功后进入图像总结阶段，总结成功后主任务进入成功状态，报告失败后前端展示失败重试入口，项目推进时能够校验前置阶段条件。系统的最终状态以数据库事实为准，前端实时事件作为状态更新的加速通道；即使 WebSocket 消息延迟或页面刷新，前端也能够通过列表接口重新恢复当前状态。

状态一致性验证还覆盖产物一致性。Reasoning 回调成功后，BIZ 会继续校验产物清单、上传状态和 SHA256 信息；只有必要产物全部上传成功，子任务才会被写入成功状态。该验证对应\cref{sec:implementation-system-state-machine-design-and-implementation}和\cref{sec:implementation-stability-design-and-implementation}中的设计，说明系统能够避免“数据库显示成功但对象存储缺少产物”的异常情况。

\section{部署验证}
\label{sec:validation-deployment-validation}

部署验证覆盖 Docker Compose 环境下的服务启动、依赖编排、环境变量配置、RocketMQ Topic 初始化、gRPC 地址配置、对象存储访问、模型目录挂载、日志采集和 WebSocket 消息推送。系统部署链路包括 RocketMQ NameServer 和 Broker、Classification、Reasoning、Summary、BIZ、API 和 Web 等服务，基础设施包括 MySQL、Redis、MinIO、RocketMQ 和日志 Sidecar 等。

部署验证结果表明，系统能够在容器环境下完成多服务启动、链路调用和页面访问。RocketMQ Topic 在业务服务启动前完成初始化，API 服务能够稳定消费项目事件；Reasoning 服务通过模型目录挂载方式读取权重文件和图像处理脚本，镜像构建、模型更新和运行环境管理边界清晰；BIZ 和 API 能够通过环境变量连接 MySQL、Redis、MinIO 和 RocketMQ；日志采集、对象存储授权和服务依赖顺序能够统一纳入 Docker Compose 编排。上述结果说明，系统具备从本地开发环境迁移到容器化运行环境的工程完整性。

上述验证也说明，智能系统的工程落地不仅包含代码开发，还包含运行环境、依赖管理、服务编排、对象存储授权和日志治理等配套工作。部署验证将这些内容统一纳入系统验证范围，进一步证明了本系统作为完整软件原型的可运行性。

\section{应用价值分析}
\label{sec:validation-application-value-analysis}

本基于 AI Agent 的建筑幕墙韧性评估软件系统在应用层面体现出四方面价值。第一，图像资产管理使大量幕墙巡检图像能够按项目和图像组维度进行组织，便于后续追踪和区域化分析；第二，Agent 自主任务调度方法减少了人工判断检测能力的成本，使系统能够根据图像内容动态执行检测任务；第三，LLM 分层信息整合策略使检测结果能够逐步转化为可读报告，降低人工整理报告的负担；第四，实时进度和结果可视化提升了用户对长任务的可理解性。

与单一检测工具相比，本系统更接近实际运维软件，它不仅告诉用户某张图是否有缺陷，还把项目、图像、检测、总结、复核和报告纳入同一个流程；与纯 Agent 应用相比，本系统具有更强的工程约束，Agent 的输出会被数据库、状态机和接口协议管理，从而使系统既具有智能性，也具有可落地性。

\label{sec:validation-chapter-summary}
