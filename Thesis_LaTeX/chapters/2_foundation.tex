\chapter{相关研究基础}
\label{chap:foundation}

本章从建筑幕墙巡检与数字化运维、幕墙缺陷检测技术、AI Agent 工程范式和韧性评估报告生成四个方向梳理本系统的相关研究基础。现有方法在单类缺陷检测能力上已经具有一定积累，但在项目级任务编排、Agent 自主任务调度和 LLM 分层信息整合方面仍存在一定空白。

\section{建筑幕墙巡检与数字化运维}
\label{sec:foundation-building-curtain-wall-inspection-and-digital-operation-and-maintenance}

建筑幕墙巡检长期以来依赖人工现场勘查。人工巡检能够结合经验进行综合判断，但在高层建筑、大面积幕墙和复杂环境下效率较低，且存在安全风险。随着无人机技术和图像采集设备的发展，基于无人机的建筑立面巡检逐渐成为重要方向。Freimuth 和 K{\"o}nig 对无人机建筑检查的规划和执行流程进行了系统研究，说明无人机能够降低高空检测成本并提升数据采集效率\cite{freimuth2018uav}。在此基础上，红外热成像、图像配准和 BIM、AI 结合等方法进一步扩展了建筑立面检测的数据来源、空间定位能力和智能分析能力\cite{li2024facade,zhang2023uavbim,leng2018bimai}。

但是，数字化采集并不等于智能化评估。无人机可以快速采集图像，但图像采集之后仍需要图像管理、缺陷检测、结果解释和报告生成。若缺少后续软件系统，采集到的图像仍然是离散资料，难以转化为运维决策。因此，建筑幕墙评估系统需要将采集后的图像组织为项目资产，并建立从图像收集到评估报告生成的完整处理流程。

从工程应用角度看，采集设备能够提高图像获取效率，检测模型能够提高局部缺陷识别效率，但真正面运维单位和工程师的交付物通常是带有结论、依据和建议的评估报告。这意味着系统需要同时处理视觉证据、结构化指标、项目语义和文本表达。若系统只停留在缺陷框或掩码图层面，仍然需要人工把这些结果重新解释、筛选、汇总和撰写。因此，图像检测之后的组织、解释和报告生成，是建筑幕墙从数字化运维走向智能化运维的关键环节。

幕墙工程对象同时具有明显的项目属性。同一种缺陷出现在不同区域，其工程意义可能不同；同一张图像中的不同材料，也可能对应不同检测任务。传统视觉检测研究往往把图像视作独立样本，而实际运维更关心项目内图像之间的关系、图像组与建筑区域的关系、缺陷分布与维护优先级之间的关系等。本文的系统设计正是围绕这种项目级应用需求展开。

\section{幕墙缺陷检测技术}
\label{sec:foundation-curtain-wall-defect-detection-technology}

在本文讨论的幕墙巡检场景中，图像是最直接也最容易获得的数据来源。算法面对的通常不是标准实验图，而是带有反光、阴影、倾斜视角、材料纹理和背景遮挡的现场照片。因此，缺陷检测一般要完成几件比较实际的工作：判断缺陷类型，给出缺陷位置，并尽量形成面积、长度、平整度或置信度等可解释指标。早期或轻量化场景中仍会使用传统计算机视觉方法，例如利用 Canny 边缘检测和 Hough 直线检测提取轮廓或线性结构，也可以结合 Sobel 梯度、Laplacian 方差、傅里叶频域分析和形态学开闭运算描述纹理突变、模糊程度或局部形态变化\cite{canny1986edge,duda1972hough}。这类方法的优点是实现过程清楚，对大规模标注数据依赖较小，在裂缝、边缘和规则构件分析中也比较容易解释；不足是对现场条件较敏感，换到另一种光照、另一类材质或另一批拍摄角度后，阈值和规则往往需要重新调整。

深度学习方法把特征提取更多交给数据本身。卷积神经网络不再手工指定每一个边缘或纹理规则，而是在训练过程中逐层形成从低级纹理到高层语义的图像表征；ResNet 等残差网络进一步通过残差连接缓解深层网络训练困难，因而常被用于图像分类任务\cite{article1,conf1}。如果任务关注“缺陷在哪里”，目标检测模型会更直接，它可以同时给出类别和位置。基于候选区域的两阶段方法，以及以 YOLO、SSD 为代表的一阶段方法，是目标检测中较常见的两条路线；国内已有综述对 R-CNN、Faster R-CNN、YOLO 和 SSD 等代表性算法进行了梳理\cite{fan2020objectdetection}。其中，YOLO 系列强调端到端和实时检测，在需要快速定位缺陷候选区域时较为适用\cite{redmon2016yolo}。

当评估需要更细的边界或面积信息时，仅有检测框往往不够，语义分割和实例分割模型会更有价值。U-Net 等编码器-解码器结构是像素级分割中的典型思路，相关文献综述已经对深度学习语义分割中的区域分类、像素分类、全监督和弱监督方法进行了总结\cite{tian2019semanticsegmentation}。DeepLabV3+ 通过空洞卷积和编码器-解码器结构提升语义分割效果\cite{chen2018deeplabv3plus}；视觉 Transformer 借助自注意力机制增强长距离依赖建模能力，为视觉识别、目标检测和视觉分割提供了新的表征基础\cite{zhou2023visiontransformer}；SegFormer 则进一步将 Transformer 表征用于高效语义分割\cite{xie2021segformer}。此外，Mask R-CNN 等实例分割方法和 Segment Anything 分别从实例掩码预测、通用分割能力等方向扩展了区域分割的使用范围\cite{su2022instancesegmentation,kirillov2023sam}。放到建筑结构和幕墙巡检中，裂缝检测、玻璃检测和表面缺陷识别已经有较多积累。Ye 等人利用深度学习方法进行结构裂缝检测，可为石材或混凝土裂缝识别提供参考\cite{ye2019crack}；Mei 等人研究真实场景中的玻璃检测问题，对玻璃幕墙区域分析也具有参考意义\cite{mei2020glass}。

\subsection{金属锈蚀检测原理}
\label{sec:foundation-metal-corrosion-detection-principle}

金属构件发生锈蚀后，图像中通常会出现颜色加深、边界不规则、局部纹理粗糙等特征。该检测能力需要定位锈蚀区域，并输出锈蚀区域数量、置信度、锈蚀像素数和锈蚀占比等指标。为了兼顾检测速度和区域精度，系统在这一部分保留了两条实现路径。一条是基于 YOLO 的检测或分割路径，适合快速获得锈蚀候选区域，并输出缺陷框、掩码和类别置信度；另一条是基于 DeepLabV3+ 的语义分割路径，将锈蚀检测建模为二分类像素分割问题，通过编码器提取图像特征，再利用空洞卷积扩大感受野，以识别边界不规则的锈蚀区域\cite{chen2018deeplabv3plus}。在代码实现中，DeepLabV3+ 使用 MobileNetV2 作为轻量化骨干网络，用于降低推理成本并适配工程部署\cite{sandler2018mobilenetv2}。

推理过程中，脚本读取原始图像后，会完成尺度变换、张量化和归一化处理，并得到锈蚀概率图。对于语义分割路径，二值掩码会根据概率分布生成：当整体概率较高时使用 Otsu 自适应阈值，其他情况下使用置信度阈值对概率图进行二值化。为减少零散噪声，脚本还会执行形态学开运算，并依据连通域或轮廓面积过滤过小区域。经过上述处理，系统可以根据掩码统计锈蚀像素数、锈蚀面积占比、区域数量和平均置信度，同时生成锈蚀覆盖图供前端展示。由此得到的锈蚀检测结果既包含可视化证据，也包含可以继续参与项目级评估的结构化指标。

\subsection{石材裂缝检测原理}
\label{sec:foundation-stone-crack-detection-principle}

石材或混凝土幕墙表面的裂缝通常较细，形态也不完全规则。现场图像中还会出现石材纹理、阴影、接缝和拍摄噪声等干扰，使裂缝边界不一定清楚。若只依赖边缘检测或固定阈值，容易把石材纹理误判为裂缝，也可能漏检对比度较低的真实裂缝。基于这一特点，裂缝检测脚本采用深度分割路线，将裂缝识别处理为像素级语义分割任务。原始系统并不是直接对整张图进行一次性判断，而是包含幕墙区域检测、区域分割和裂缝分割等步骤；其中可结合 YOLO 旋转框模型、MobileSAM 或 SegFormer 等能力，先获得相对稳定的石材候选区域，再由裂缝分割模型输出裂缝掩码\cite{xie2021segformer,kirillov2023sam}。

在裂缝分割阶段，图像经过预处理后输入分割模型，模型输出每个像素属于裂缝类别的概率。后处理部分会将概率图转化为二值掩码，并完成尺寸恢复和高亮叠加，形成裂缝覆盖图、裂缝掩码图和裂缝区域统计结果。相比只输出目标检测框，像素级掩码能够更细致地表达裂缝长度、宽度和空间走向，也便于进一步计算裂缝像素数和裂缝占比。对后续评估而言，这类结果比单纯判断“是否存在裂缝”更有使用价值。

\subsection{石材污渍检测原理}
\label{sec:foundation-stone-stain-detection-principle}

石材污渍与裂缝的视觉形态有所不同。裂缝多表现为细长线状结构，污渍则通常来自污染、渗水痕迹或颜色异常，呈现块状或片状变化，边界不一定清晰，并且容易受到拍摄角度和透视变形影响。若直接在整张图像上计算污渍比例，不同幕墙块的倾斜程度会影响面积统计的准确性。为降低这一影响，污渍检测脚本采用“幕墙块分割、透视校正、局部污渍分析”的组合路线。脚本先使用 YOLO 模型对图像中的幕墙块进行实例分割，得到每个候选幕墙块的掩码；之后根据掩码轮廓计算凸包，并通过多边形近似寻找四个角点；当角点按照左上、右上、右下、左下的顺序排列后，系统即可利用透视变换将倾斜拍摄的幕墙块校正为正视局部图像。

完成透视校正后，局部幕墙块会进入传统图像处理算法，用于估计污渍面积。原始脚本调用污渍分析模块，计算每个校正块的污渍比例，并生成对应的结果图像。不同输出图像承担的作用也不相同：整体标注图用于查看所有候选幕墙块的位置，局部校正图用于确认检测区域，结果图用于展示污渍分析效果。该方法将深度学习模型用于区域定位，将传统图像处理用于比例计算，二者分工较为清楚。由此得到的“平均污渍占比”和“最高污渍占比”不只是整图层面的粗略统计，而是具有相对明确的区域含义。

\subsection{玻璃平整度检测原理}
\label{sec:foundation-glass-flatness-detection-principle}

玻璃平整度检测关注玻璃幕墙中可能出现的局部变形、反射异常或不平整现象。与裂缝、锈蚀不同，玻璃平整度问题在图像上往往缺少明确的缺陷边界。由于玻璃具有透明、反光和低纹理等特点，真实的不平整更可能表现为边缘畸变、直线偏折、梯度分布异常或频域能量变化。基于这些视觉特征，脚本采用“玻璃区域识别 + 多特征规则判别”的实现路径，而不是直接使用单一分类结果。系统会先通过玻璃检测或分割模型获得玻璃区域，再将后续分析限制在局部区域内，以减少背景和窗框对判断的干扰。

在局部玻璃区域中，脚本先进行裁剪，再使用 Canny 方法提取边缘，并计算边缘数量和 Laplacian 方差，用于反映局部纹理和清晰度变化\cite{canny1986edge}。直线分析部分通过概率 Hough 变换检测线段，并统计线段角度标准差，用于判断反射线或边缘线是否出现异常偏折\cite{duda1972hough}。梯度分析利用 Sobel 算子计算梯度幅值，并统计梯度均值和梯度标准差；频域分析则对灰度图执行离散傅里叶变换，观察频谱能量差异。系统将直线、梯度和频域三个判别结果进行融合，并通过多数投票得到玻璃是否不平整的结论。

\subsection{玻璃爆裂检测原理}
\label{sec:foundation-glass-spalling-detection-principle}

玻璃爆裂检测在系统中对应一个二分类任务，用于判断玻璃幕墙图像中是否存在破裂、爆裂或碎裂风险。脚本采用基于 ResNet34 的二分类模型，将输入图像划分为“存在缺陷”和“不存在缺陷”两类。模型以 ResNet34 作为骨干网络，并将末端全连接层替换为二分类输出层。推理时，图像会被缩放到 $224\times224$，转换为张量后按照 ImageNet 均值和标准差进行归一化，再输入模型得到类别预测。

虽然上层系统看到的是一个二分类接口，但该能力仍依赖较完整的数据准备和训练前处理流程。数据清洗阶段会检查图像完整性、文件重复、分辨率、标注缺失和拍摄角度；数据增强阶段使用旋转、水平翻转、缩放、亮度对比度扰动、高斯噪声、椒盐噪声和透视畸变等方式，提高模型对不同拍摄条件的适应能力；数据划分阶段则按照工程类型、区域和年份构造分层键，再将数据划分为训练集、验证集和测试集。原始脚本中还保留了基于 Canny 与 Hough 直线的辅助处理，用于过滤与横纵轴近似平行的线性纹理干扰。由此可见，玻璃爆裂检测虽然在系统中呈现为简单分类结果，但背后仍包含数据治理、数据增强和模型训练等多个环节。

综上，五类原子检测能力在技术路线和输出形态上存在差异：金属锈蚀和石材裂缝更偏向分割，石材污渍结合了实例分割与透视校正，玻璃平整度依赖多种视觉特征融合，玻璃爆裂则采用深度分类模型。本文将这些差异封装在统一的原子能力接口之后，使上层 Agent 不需要感知每个算法的内部实现，而只需要基于图像内容选择任务代码并接收结构化结果。这也是本文从单点检测算法走向工程化智能评估系统的基础。

\section{从单点检测到项目级评估的差距}
\label{sec:foundation-single-algorithm-to-project-level-assessment-gap}

已有幕墙缺陷检测研究通常以单一任务为目标，例如裂缝识别、玻璃检测或表面污渍检测。这类研究能够回答算法层面的问题：给定输入图像，模型是否能够准确输出目标区域。然而，项目级评估需要回答更复杂的问题：哪些图像需要执行哪些检测，多个检测结果之间如何互相补充，哪些缺陷对项目整体风险影响更大，报告中应如何表达证据与结论之间的关系。

如\cref{fig:foundation-single-detection-to-project-assessment-transition} 所示，从单点检测到项目级评估之间至少存在四个缺口。第一是数据组织缺口，图像需要按照项目、图像组、图像和检测任务多层组织。第二是任务编排缺口，系统需要根据图像内容动态选择检测能力，而不是机械执行全部模型。第三是结果解释缺口，模型输出的像素和坐标指标需要转化为工程语言。第四是报告生成缺口，系统需要把多张图像的局部结论融合为项目级评估意见。本文的研究价值正是在这些缺口处构建桥梁。

\section{AI Agent 的发展与工程范式}
\label{sec:foundation-artificial-intelligence-agent-development-and-engineering-paradigm}

大语言模型出现以后，Agent 逐渐成为人工智能应用中的一种重要组织方式。与早期主要用于文本生成和问答的模型不同，Agent 更关注模型如何围绕用户目标与外部工具、运行环境和任务反馈发生交互。ReAct 将推理过程和行动过程放在同一条链路中，使模型可以在形成思路的同时执行具体任务动作\cite{yao2023react}。Toolformer 则进一步讨论了语言模型学习工具使用的问题，包括何时调用工具、如何传递参数以及如何利用工具返回结果\cite{schick2023toolformer}。从这些研究可以看出，大语言模型要进入实际任务场景，不能只依靠自然语言生成能力，还需要通过工具调用机制把语义理解转化为可执行操作。

在工业界和开源社区中，Agent 也逐渐从单次问答走向工作流开发。AutoGen 通过多智能体对话组织复杂任务，使不同角色、不同能力的 Agent 可以作为可编程组件参与协作\cite{wu2023autogen}。相关综述也指出，大语言模型 Agent 可用于单智能体、多智能体和人机协作等场景，规划、记忆、工具使用和反馈学习是其中较为核心的能力\cite{wang2023llmagents}。不过在工程系统中，Agent 通常不会被设计成完全自由行动的主体，而是需要放入受控流程中运行。结构化输入输出、工具白名单和状态管理等机制，能够为 Agent 的调用边界、执行过程和结果回收提供约束。

本文正是基于这一认识，将 Agent 设计为业务链路中的受控智能节点。分类 Agent 不是自由选择任意工具，而是在预定义五类任务代码中选择；总结 Agent 不是直接修改系统状态，而是通过回调接口提交总结结果；项目报告 Agent 不是自行读取数据库，而是接收由 BIZ 服务组织好的项目上下文。这样的设计符合当前 Agent 工程化趋势：让模型承担语义理解和决策任务，让工程系统负责边界和状态。

\section{Agent 工程化的可控性问题}
\label{sec:foundation-agent-engineering-controllability-problem}

Agent 引入工程系统后，可控性问题会比普通问答场景更突出。此时模型是否“答得像样”并不是唯一标准，更重要的是它的输出能否被后端服务稳定解析，能否与数据库状态、任务队列和人工复核流程对齐。大语言模型本身具有概率性，实际使用时可能出现格式不稳定、内容越界、幻觉或工具选择错误等情况。例如，同一类请求在不同轮次中可能出现字段缺失、字段命名变化，或者把解释性文字混入结构化结果中。已有研究对幻觉问题进行了较多讨论，其风险在于模型生成的内容表面上较为合理，但缺少事实依据，放入真实系统后会影响信息可靠性\cite{huang2023hallucination}。

在工具调用场景中，这类风险还会继续向后传递。模型不仅要理解用户目标，还要判断调用时机、工具类型和参数组织方式；如果工具选择错误，后续 Worker 就可能执行不适合当前图像的检测任务。Toolformer、ToolLLM 等研究表明，大语言模型可以学习或增强工具使用能力；但从工程角度看，这也意味着工具使用能力不能只依赖模型自由发挥，而要依赖工具集合、调用路径和评估机制进行约束\cite{schick2023toolformer,qin2023toolllm}。如果只是普通问答系统，上述问题更多体现为回答质量波动；如果 Agent 的输出会进一步影响数据库状态或任务调度，就可能带来错误流程。因此，结构化输出、工具白名单、状态隔离和人工复核，是 Agent 工程化中必须处理的基础问题。

如\cref{fig:foundation-agent-engineering-risk-control-mechanism} 所示，针对上述风险，现有研究和工程实践通常会从动作、输出和流程三个层面进行约束。这里的约束并不是简单减少 Agent 的能力，而是把模型适合完成的语义判断留给模型，把状态推进、数据落库和异常恢复交给工程系统处理：

\begin{enumerate}
  \item 一是限制动作空间，让 Agent 只能在预定义工具、API 或任务代码中选择。动作空间越开放，错误工具选择后的影响就越难控制；而有限动作空间可以把模型输出收敛到工程系统能够识别和处理的范围内。ReAct 通过推理与行动交替形成较清晰的行动轨迹，AutoGen 则通过多 Agent 对话和人类参与机制组织复杂任务流程\cite{yao2023react,wu2023autogen}；
  \item 二是约束输出格式，使模型结果能够被程序稳定解析。自然语言回答对用户阅读比较友好，但对后端程序并不稳定，因此工程系统通常需要固定字段、类型检查和解析校验。PICARD 通过增量解析约束自回归解码，Outlines 相关研究则将文本生成表示为有限状态机转移，并借助正则表达式或上下文无关文法限制生成结构\cite{scholak2021picard,willard2023efficient}；
  \item 三是把 Agent 放入受控工作流，由工程系统负责状态推进、失败重试、日志记录和人工复核。即使 Agent 的输出格式正确，也不能说明它可以直接修改业务状态。更稳妥的方式是让 Agent 提供判断结果，由业务服务决定结果何时生效、失败如何记录、是否需要人工复核。相关综述也指出，LLM Agent 的规划、工具使用和反馈机制需要与评估和控制机制共同设计，才能进入可靠应用\cite{wang2023llmagents}。
\end{enumerate}

本文采用的思路是将 Agent 决策限制在有限动作空间内。分类 Agent 只能输出五种任务代码的组合；图像总结 Agent 的结果只作为总结字段保存，不直接修改检测状态；项目报告 Agent 接收的输入由 BIZ 服务生成，输出也通过固定回调进入数据库。这样做牺牲了一部分开放性，但换来了工程系统所需的确定性和可追踪性。对于建筑幕墙评估这种专业场景，这种受控形式是 Agent 自主任务调度方法能够落地的基础。

\section{工程软件中的异步任务编排}
\label{sec:foundation-engineering-software-asynchronous-task-orchestration}

长耗时任务编排是智能检测系统必须解决的问题。模型推理、外部 Agent 调用、对象上传和报告生成都可能持续数秒到数分钟，若采用同步 HTTP 请求等待全部结果，系统容易超时，用户体验也较差。成熟工程系统通常采用任务队列、Worker、回调和状态查询机制，将“启动任务”和“获得结果”解耦。

本文系统采用类似思想，并针对 Agent 调用链路做了扩展。用户在前端启动检测后，BIZ 服务并不等待所有模型和 Agent 返回结果，而是先创建检测任务、写入初始状态，再把任务投递到队列中。后续的分类、推理和总结由不同 Activity 服务分段处理，处理完成后再通过回调把结果写回业务服务。前端则通过 WebSocket 接收状态变化。这样设计以后，用户不需要停留在一次长时间的 HTTP 请求中等待，后台服务也可以把每一步的执行结果单独记录下来。

异步任务编排对本系统比较关键，原因在于 Agent 调用和模型推理都存在一定不确定性。Agent 平台可能遇到网络波动、限流或输出格式异常；视觉模型可能因为图像格式、模型加载或运行环境问题失败；对象存储上传也可能受到网络状态影响。如果把这些步骤全部放在一次同步请求里，只要中间某一步失败，整个请求就会直接结束，用户也很难知道失败发生在哪个环节。采用任务状态机和回调机制后，系统可以把这些情况落到具体状态上，例如等待中、执行中、失败、成功等，前端也能据此展示进度和错误原因。

从软件工程角度看，异步任务编排不只是为了避免接口超时，也是在表达本系统内部的业务依赖关系。检测主任务、检测子任务、总结任务和报告任务并不是平行关系，而是有先后条件。例如，分类失败时不应继续创建检测子任务；检测子任务全部完成后才适合进入总结阶段；如果某张图没有需要执行的检测子任务，也应直接进入相应的完成状态。把这些关系写入数据库状态和 Worker 编排逻辑后，系统才能按规则推进，而不是依赖某一次请求过程中的临时判断。

\section{LLM 信息整合与报告生成}
\label{sec:foundation-large-language-model-information-integration-and-report-generation}

大语言模型擅长自然语言生成，但在知识密集型任务中，输入信息的组织方式直接影响输出质量。检索增强生成通过外部知识库向模型提供上下文，缓解模型仅依赖参数知识导致的不可靠问题\cite{lewis2020rag}。与此类似，工程报告生成也需要将外部数据组织成适合模型处理的上下文。如果输入过少，报告缺少依据；如果输入过多，模型容易遗漏重点或产生不稳定输出。

建筑幕墙韧性评估报告属于典型的多源信息整合任务。其输入包括项目基础信息、图像组信息、原子检测指标、图像产物、区域级数据、用户复核评论和任务状态。直接把这些信息一次性提交给大语言模型并不合理，因为底层指标数量可能随图像数量和区域数量快速增长。本文提出 LLM 分层信息整合策略，将报告生成拆分为图像级和项目级两个阶段。该策略并非简单压缩文本，而是根据工程评估逻辑先形成单图语义，再进行项目级融合。

\section{本章小结}
\label{sec:foundation-chapter-summary}

本章围绕幕墙巡检、缺陷检测、Agent 工程范式、异步任务编排和 LLM 报告生成等内容进行了梳理。可以看到，现有研究已经为单类缺陷识别和通用 Agent 工具调用提供了较多方法基础，但与本文面向的项目级幕墙评估场景相比，仍有一些不完全匹配的地方。幕墙检测研究更多回答“某张图是否存在某类缺陷”，对图像资产如何按项目组织、检测任务如何根据图像内容调度、检测结果如何进入报告链路讨论较少；Agent 相关研究多从通用工具调用、代码执行和问答协作展开，落到建筑工程软件时，还需要进一步处理状态管理、失败恢复、权限边界和人工复核等问题；大语言模型报告生成则常关注文本生成效果，对输入信息分层、数据库状态和业务流程之间的配合说明不足。

因此，本文的切入点不是单独改进某一个检测模型，也不是把 Agent 作为额外的问答入口，而是把已有检测能力、Agent 任务调度和工程系统组织起来，形成从图像资产到韧性评估报告的完整链路。本文系统希望进一步回答三个更贴近业务流程的问题：单张图应该执行哪些检测，检测结果怎样形成可读的图像总结，多个图像结果和复核信息又怎样汇总为建筑级韧性评估报告。围绕这些问题，后续章节将从需求建模、方法设计和系统实现三个层面展开说明。
